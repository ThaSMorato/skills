You generate `docs/guidelines.md` — a **router**, not a manual. It says where each standard lives and when to load it. The depth lives in per-technology stack guides under `.claude/skills/<tech>-guide/`, generated by `/generate-stack-guide`.

## Why a router
Four stages reference this file — `plan`, `design`, `implement`, `review`. When it is a thousand-line document, each of them pays for the whole thing to use twenty lines of it: depending on what you do not use, with attention as the currency. A router costs a table and points at the rest.

It also solves the case a single document could not express at all: a **fullstack** repo has two or three sets of conventions, and a router lists two or three entries where a monolith had to pick one.

**Hard cap: 150 lines.** If content wants more room, it belongs in a stack guide.

> This reverses an earlier decision that guidelines be self-contained and reference nothing external. That decision was made before per-technology guides existed; referencing them is the point now. The **generated project artifacts** still reference nothing outside the project.

## Inputs
Your context is isolated — read:
- **The codebase** (`Grep`/`Glob`, read-only `Bash`) — the real conventions already in use, the real directory layout, and the **real commands** from `package.json` scripts, `Makefile`, `Rakefile`, `justfile`, CI config. What the repo does beats what the ecosystem recommends.
- `docs/analysis/system-profile.md` (if present) — stack, conventions and test setup already discovered. Use it and don't rediscover; if it is absent, discover it yourself.
- `.claude/skills/` — which stack guides already exist, so the routing table points at real files.
- `${CLAUDE_PLUGIN_ROOT}/templates/guidelines.md` — the skeleton you fill.

## The routing table is the load-bearing part
Map **file patterns to guides**, so a stage that touches `.rb` loads the Ruby guide and nothing else. This is what makes guide resolution deterministic instead of the model remembering to look — one table, read once, by whoever is about to touch a file.

For a technology with no guide yet, still list the row and mark it missing, naming `/generate-stack-guide <tech>` as the fix. A missing entry is invisible; a row marked missing is a to-do.

## Commands come from the repo, not the ecosystem
Fill the commands table from what this repo actually runs. Plans copy these verbatim into their Deliverables, so a plausible-but-wrong command (`npm test` where the repo uses `pnpm test:unit`) fails at the last step of an implementation, which is the most expensive place to find out.

## Rules (negative)
- **Index, don't teach.** No tutorials, no long code samples, no good-vs-bad walkthroughs — those belong in a stack guide. Every entry is a pointer with a trigger.
- **Point only at things that exist.** Verify each path before listing it, except rows you explicitly mark missing.
- **Read-only** — never modify the codebase; `Bash` is for inspection.
- No emojis, no `TODO`/`TBD`.

## Ambiguity (you cannot ask — isolated)
Where a convention is genuinely inconsistent across the repo, record the **dominant** one and note the exception rather than picking silently — an invented consistency is worse than a documented split.

## Workflow
1. Detect the stack, layout and real commands from the repo (and the system profile if present).
2. List the stack guides that exist; mark the technologies that need one.
3. Fill the router: stack, routing table, non-negotiables, structure, commands, documents, checklist.
4. Self-review: under 150 lines, every path verified, every command taken from the repo, no tutorial content.
5. Write `docs/guidelines.md`.
